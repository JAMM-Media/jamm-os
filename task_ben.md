## WHAT IS WRONG

Confirmed via the [CONCIERGE RAW] log: streamed responses break mid-sentence
at regular intervals, e.g. "which we" then a line break then "are currently
working on." The draft content itself is clean in the model output, so the
breaks are inserted during streaming, not generated by the model.

Root cause: the streaming generate() path treats each token fragment from
stream.text_stream as if it were a full line. It runs text.split("\n") on a
fragment that usually contains no newline, wraps it as a data: event, and
the frontend assembleSSELines appends a \n after every data: event. The net
effect is a line break inserted at every token chunk boundary, which falls
mid-sentence.

The tool path does not have this bug because it splits the complete final
text on real newlines and emits one event per actual line. The two paths
disagree about what a data: event represents. The frontend correctly assumes
one-event-per-line, so the fix belongs in the streaming backend path, which
must be brought in line with the tool path rather than emitting per-fragment
events.

## ACTION

File: /home/corby/jamm-os/app/api/concierge/route.py

In the streaming generate() path (the block iterating stream.text_stream),
stop emitting a data: event per token fragment. Instead accumulate the full
text first, then emit one data: event per real line, exactly matching the
tool path's proven approach.

Replace:

            assembled = ""
            for text in stream.text_stream:
                assembled += text
                data_lines = "\n".join(f"data: {line}" for line in text.split("\n"))
                yield f"{data_lines}\n\n"

with:

            assembled = ""
            for text in stream.text_stream:
                assembled += text
            for line in assembled.split("\n"):
                yield f"data: {line}\n\n"

Leave the filter_output block, the [FILTERED] sentinel logic, and the
[TOPIC:...] trailing marker that follow exactly as they are. They already
operate on the fully assembled text and are unaffected. Do not change the
tool path. Do not change the frontend assembleSSELines. Do not touch any
other file.

Note: this changes the streaming path from incremental token streaming to
emitting the full response once complete. This is the same delivery model
the tool path already uses. The visible tradeoff is the response appears all
at once rather than typing in progressively. This is acceptable and correct
for now because the current per-token streaming is actively corrupting the
output, and a clean non-streamed response is strictly better than a
progressively-rendered corrupted one. If progressive streaming is wanted
back later, it requires buffering whole lines before emitting, which is a
separate larger change.
